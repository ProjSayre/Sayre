## 1. Project Overview & Core Value Proposition

Modern development teams face massive friction when onboarding engineers, managing context switching, and aligning technical architecture with product objectives. Current tooling treats repositories as flat file structures or disconnected documentation.

This platform is an AI-powered, context-aware codebase ontology and visualization web application. By parsing codebases into interactive, multi-dimensional knowledge graphs, the platform translates raw source code into tailored "tree maps" for different organizational stakeholders (technical, product, onboarding). It solves the "kitchen without labels" dilemma by mapping explicit code dependencies, task management tickets, ownership history, and required skills directly onto a visual graph canvas.

The same knowledge graph that powers the human-facing canvas is also exposed as a live context layer for external AI coding agents (§1.3), and the models that build and query that graph are themselves swappable — including to models an organization runs entirely on its own infrastructure (§2.7).

### 1.1 Target Audience

- **New Hire Engineers** — Accelerate time-to-productivity by visualizing branch-specific context, architectural dependencies, and onboarding workflows — including team/feature-scoped onboarding via Buckets (§2.11).
- **Technical Leads & Architects** — Maintain a clear structural map of code semantics, identify ownership, track style adherence, enforce modular boundaries, author the Agent/Skill MD rules that govern how AI agents may modify each part of the codebase, and curate the Onboarding Buckets representing their teams (§2.11).
- **Product Managers** — Track feature shipping progress and map Jira/Linear tasks directly to real-world code components, including via the org-wide Ticket Inbox (§2.9).
- **AI Coding Agents** — Claude Code, Cursor, and other MCP-compatible agents — including a customer's own agents running on self-hosted models — consume the graph as structured context.
- **Security & Compliance Reviewers** — Organizations with data-residency or vendor-exposure requirements evaluate the self-hosted model option (§2.7) as a structural, not contractual, guarantee that source code never leaves their environment.

### 1.2 Macro View: Multi-Repo Architecture

Before any file tree renders, the platform supports a highest-level, multi-repo view of how work is actually organized across an engineering org. This Macro View is its own graph layer, sitting above the Unified File Skeleton (§4.3), and is what a viewer lands on before drilling into a specific repo's Technical/Product/Onboarding Tree.

- **Project-to-Repo Mapping** — A Project maps to one or several repositories.
- **Inter-Repo Context** — Repositories are connected by cross-repo edges, inferred from detected API contracts, shared package versions, and cross-repo import statements.

Selecting a Repo node drills into that repo's Unified File Skeleton, preserving the Technical/Product/Onboarding view toggle (§2.2). See §4.3 for Project/Repo node and edge additions.

### 1.3 The Agent Context Layer

The strategic observation behind this addition: the moat is the graph, not the agent. Rather than building a competing agent, the platform exposes its graph to every agent through MCP — including agents built on a customer's own models (§4.11).

- The canvas is where humans understand and configure — architecture, ownership, feature descriptions, Agent/Skill MD (§4.8), folder-level style rules (§4.9), and Onboarding Buckets (§2.11).
- MCP is where agents act — find relevant nodes, pull bounded context, read Agent/Skill MD for any node they intend to touch, resolve effective style rules, identify covering tests — bound by the same RBAC and tenant isolation a human session is bound by.

The MVP MCP surface is read-only. Write-path tools are post-MVP and trigger-gated (§7).

## 2. Functional Requirements — with Required Tooling

### 2.1 Unified Graph-Based Repository Parsing

- **Multi-Language AST Parsing** — Tree-sitter, Python, JS/TS/Py/Go grammars to start.
- **Semantic Relationship Extraction** — Graphify constrains LLM output into graph primitives so enrichment results merge directly into the graph store rather than returning free-form prose. Holds regardless of which model, hosted or self-hosted, sits behind the call (§2.7). Tooling: Graphify, LangChain/LangGraph, a pluggable model backend, Python/FastAPI.
- **Delta Processing** — Incremental processing on every push. Tooling: GitHub Webhooks, Python, SQS.

### 2.2 Multi-View Interactive Tree Canvas

Canvas Node Model: exactly two node types — Folder ("F") and File (including API endpoint files). Functions/classes are graph data but never their own canvas nodes.

| View | Target Users | Scope | Tooling |
|---|---|---|---|
| Technical Tree | Architects, Core Devs | Syntax hierarchies, data models, infra nodes, imports, API routing paths — plus live-presence highlighting (§2.12) | React Flow, Sigma.js (WebGL) + graphology, TypeScript |
| Product Tree | PMs, UX | High-level feature groupings mapping files to user-facing capabilities | React Flow, Next.js, Tailwind CSS |
| Onboarding Tree | New Hires, DevOps | Sequenced setup workflows, dependencies, required dev environments — global or Bucket-scoped (§2.11) | React Flow, Next.js API routes, sandboxed shell execution |

**Renderer decision:** React Flow for <~500 visible nodes; Sigma.js (WebGL) above that threshold, chosen automatically from a backend node-count signal. graphology handles client-side algorithm gaps behind a documented allowlist; RBAC filtering and deep traversal always remain server-side.

### 2.3 Context & Metadata Labeling Engine

- **Ownership & Git History** — GitHub REST API, git log parsing, Node.js/TypeScript.
- **Coding Style & Guidelines** — LLM classification via the pluggable model backend (§2.7), PostgreSQL metadata store.
- **Onboarding Automation** — Next.js, containerized/sandboxed runner, PostgreSQL.

### 2.4 Asynchronous Tooling Integrations

**GitHub Integration** — Native GitHub App authorization capturing live commits, pull requests, and branch creations via webhooks.
- Delta sync latency target: <5s from webhook receipt to canvas patch.
- Org-exclusive repo scoping (hard requirement): every repository is bound to exactly one org's GitHub App installation, checked server-side on every ingestion write and read — never inferred solely from which installation's webhook delivered an event.
- Paginated reconciliation, no hard cap: the previous 25-repository-per-callback ceiling is replaced by paginated, async reconciliation with a visible partial-sync state in the UI.
- Tooling: GitHub Apps/OAuth, Webhooks, Node.js/TypeScript.

**Task Management Integration** — Bidirectional syncing via Jira REST API and Linear API, fully real-time and webhook-driven, targeting <5s ticket-to-graph latency, matching the GitHub target.
- Space/project-level org scoping (hard requirement): a Jira/Linear connection is scoped to an explicit, admin-selected allow-list of projects/spaces, not the whole connected site/workspace.
- Tooling: Jira REST API, Linear API (GraphQL), Node.js/TypeScript, BullMQ.

**Provider-Generic Git Integration** (hard requirement) — The git Integration Worker carries a `provider` field, a normalized event schema, and pluggable auth from its first version, so a second git-hosting provider (Cursor Origin, §6) is a plug-in, not a pipeline rewrite.

### 2.5 Persistent Memory & Token-Optimized RAG Architecture

- **Graph-Guided Retrieval** — The AI only retrieves code from nodes adjacent to the active file/branch, avoiding whole-repo dumps — the mechanism behind the 70x token-reduction KPI. Tooling: LangGraph, Neo4j Cypher (openCypher-only, Neptune-compatible), a pluggable model backend, Python/FastAPI.
- **Hybrid Storage Engine** — Amazon RDS (PostgreSQL), Neo4j (Neptune later), pgvector (OpenSearch later).

### 2.6 Agent Context Provision over MCP

Read-only v1 tool surface:

| MCP Tool | What it returns |
|---|---|
| `find_relevant_nodes(query)` | Graph nodes most relevant to a natural-language task description |
| `get_node_context(node_id)` | Bounded context for a node: description, structural neighbors, key metadata |
| `traverse_from(node_id, intent)` | The bounded-hop neighborhood relevant to a stated intent |
| `get_agent_skill_md(node_id)` | The node-scoped Agent/Skill MD: allowed tools, required context, guardrails |
| `get_style_rules(node_id)` | The node's effective Coding Style/Comment Style, resolved through folder inheritance |
| `get_covering_tests(node_id)` | Test nodes linked via COVERS edges, with freshness/status |
| `get_feature_cluster(node_id)` | The Feature cluster(s) the node belongs to, with member lists |
| `get_recent_changes(node_id)` | Recent editors, commits, and linked PRs scoped to the node |

Every MCP tool is a thin wrapper over the same service layer the REST endpoints call. Every call is authenticated (per-org scoped keys), RBAC-filtered, and tenant-isolated identically to a human canvas session — this holds regardless of what model or client software is on the agent side of the connection (§4.11). Tooling: MCP over streamable HTTP, Node.js/TypeScript, existing Graph Query Service.

### 2.7 Pluggable Model Provider Layer

Every LLM call point — the Semantic Enrichment Worker and the Graph-Guided RAG chatbot — sits behind a Model Provider abstraction rather than a hardcoded Anthropic call. Three supported shapes, per org:

- **Anthropic (Claude)** — the default.
- **OpenAI (GPT)** — a second hosted option.
- **Self-hosted / local** — a customer-supplied, OpenAI-compatible chat-completion endpoint (Ollama, vLLM, TGI, or equivalent), running on the customer's own infrastructure. Covers a stock open-weight model or a customer's own fine-tune, run entirely on infrastructure the platform never touches.

**Structural vs. contractual data sovereignty:** hosted providers offer a contractual guarantee — the request necessarily leaves the customer's network and the vendor's terms govern what happens to it. The self-hosted option offers a structural guarantee — no vendor server is ever in the request path, so there is no third party to trust a policy from. This is a verified, testable property (§4.2): when configured for self-hosted, the adapter makes zero outbound calls to any third-party model endpoint, confirmed by a network-isolated test.

**Known tradeoffs, stated for customers:** smaller/narrowly fine-tuned self-hosted models may produce noisier structured output than Claude/GPT; latency/uptime for a self-hosted endpoint is the customer's responsibility, with consequences for the 15s legacy sync target and the RAG chatbot; a circuit-breaker/timeout pattern around self-hosted calls degrades gracefully rather than blocking ingestion or the chatbot outright.

### 2.8 AI-Inferred Ticket-to-File Matching

Mechanical tag matching (`[sayre:file:...]` / `[sayre:feature:...]`) remains the default, zero-cost linking path. When a synced ticket carries no explicit tag, a formal, reviewed semantic-matching pipeline runs:

- The ticket's title + description are embedded through the org's configured `EmbeddingProvider` and matched against the org+repo-scoped `code_embeddings` index via cosine similarity.
- A match is only written back as an inferred `TicketReference` above a tuned, documented confidence threshold, validated against a real evaluation set of ticket/code pairs before shipping to any customer.
- Every inferred match is visually distinguished from a mechanical/explicit match on the canvas and in the Ticket Inbox (§2.9), and is user-correctable (confirm, reject, or repoint).
- A wrong auto-link is treated as worse than no link: the design defaults to single-best-match-only, and a low-confidence result surfaces the ticket as unmatched in the Ticket Inbox rather than guessing.
- This path is a first-class, audited exception to the platform's normal async fleet-split direction and is subject to the same adversarial security review as any `SECURITY DEFINER`/RLS-adjacent change.

### 2.9 Ticket Inbox

A dedicated, org-wide surface — separate from any single node's overlay panel — listing every ticket synced from every connected Jira/Linear space for that org, regardless of node linkage:

- Filterable by status, project/space, linkage state (explicit / AI-inferred / unmatched), and confidence band for inferred matches.
- An unmatched or low-confidence ticket is never simply invisible.
- Clicking a linked ticket jumps to its node; clicking an unmatched ticket offers manual linking.
- Respects the same RBAC/tenant-isolation boundary as every other graph-adjacent view.

### 2.10 Unified Login

A dedicated, polished `/login` page offering:

- Sign in with GitHub (existing OAuth flow, hardened per §4.5).
- Sign in with Google (OAuth 2.0, new provider).

Both paths issue the same session shape and both are bound to the initiating browser (§4.5). Account linking rule: if a Google and a GitHub login resolve to the same verified email, they resolve to the same platform user rather than silently creating a duplicate org/user pair.

### 2.11 Onboarding Buckets

The repo-wide Onboarding Tree (§2.2) is useful for a new hire's first day, but not for someone joining an existing team or picking up a single feature area. Onboarding Buckets add a second, narrower onboarding surface underneath it.

**What a Bucket is:** a grouping of Folder/File nodes representing a team or feature area — e.g. "Payments team," "Onboarding flow," "Infra."

**Manual configuration (Technical Lead only):**
- Built via drag-and-drop directly on the Technical Tree canvas — dropping a Folder adds everything beneath it recursively.
- Only the Technical Lead role (or an org admin) can create, edit, or delete a bucket. Regular members can view buckets they have canvas access to but cannot modify membership.
- A bucket card shows: member profile pictures in the top-right corner (Team Lead's picture first, visually distinguished from regular members), the current file/folder list, and an editable description.

**Auto-Generated Buckets:** Buckets don't require a Technical Lead to build the first draft by hand. On a repo's initial cold-start ingestion, once Feature Clustering (§2.1) finishes grouping Folder/File nodes into Feature clusters, the platform automatically creates one real Bucket per Feature cluster, pre-populated with:
- Name and description seeded from the Feature cluster's own properties.
- File membership seeded directly from the cluster's members.
- Team Lead, best-effort inferred from existing ownership metadata where a clear signal exists; left unset otherwise.

These are real, immediately usable buckets the moment Feature Clustering completes — not suggestions in a pending queue — including being immediately selectable for bucket-scoped onboarding. Each is visibly badged "Auto-generated" to distinguish it from a Technical-Lead-authored one. A Technical Lead can decline an auto-generated bucket at any time — declining deletes it outright, no soft-archived/hidden state. A Technical Lead can otherwise edit an auto-generated bucket exactly as they would a manual one; the origin property (§4.3) persists as an audit trail regardless of later edits but does not affect the bucket's capabilities.

**Two onboarding scopes, not one:**
- **Global onboarding** — the full repo-wide EnvStep sequence, still the default entry point.
- **Bucket onboarding** — a shorter EnvStep sequence scoped to only the files/folders in a specific bucket.

A user landing on the Onboarding Tree picks Global or a specific bucket before the walkthrough begins.

**Use case:** "I'm joining the Payments team, not the whole company's codebase — show me who's on it, what files are theirs, and only the setup I actually need" — with that team's bucket already there, auto-generated, waiting for the new hire on day one.

### 2.12 Live Presence on the Technical Tree

The Technical Tree (§2.2) currently reflects the graph's last-synced state — accurate, but static between syncs. A live layer sits on top of it, showing who is actively working where right now, not just who last touched a file historically (which §2.3's ownership metadata already covers).

- **Active-work highlighting:** nodes and edges tied to files with commits on a currently-open branch are recolored (or given a distinct border/glow treatment) and attributed to the contributor working there — an avatar or color key identifies who. Multiple simultaneously-active contributors get distinguishable colors.
- **In-progress (not-yet-merged) nodes:** a new file/folder on an open branch that doesn't exist on the default branch yet renders as a distinct "tentative" node (dashed border) extending from its parent, rather than being absent or indistinguishable from merged code. Removed if the branch closes unmerged; converts to a normal node automatically on merge.
- **Freshness:** driven off the same real-time GitHub sync established in §2.4 (<5s target) — branch push events, not just merge events, feed this layer.

**Use cases:** (1) picking up a ticket and immediately seeing whether someone else is already active in that part of the codebase before starting work; (2) a general "what's the team working on right now" view of the whole codebase.

## 4. System Design Architecture

Three principles drive every decision:
1. The graph is the source of truth, not the repo.
2. The write path and read path are fully decoupled.
3. Every consumer surface is a projection, not a separate dataset — and every model call is a swappable backend, not a hardcoded vendor.

### 4.1 Logical Architecture

The browser client (Next.js + React Flow/Sigma.js) talks to an API Gateway that enforces auth and RBAC, routing to a Core App Service (Node.js) for fast synchronous reads/writes, and to a Realtime Service (WebSocket + Redis pub/sub) for live graph updates — including the live-presence layer (§2.12). An MCP Gateway sits beside the API Gateway, terminating MCP connections from external agents and routing tool calls into the same Core App Service functions. Heavy work — parsing, semantic enrichment, AI retrieval — runs asynchronously in a Python/FastAPI worker fleet coordinated through SQS, with Node integration workers on BullMQ. Model calls route through the Model Provider Adapter to whichever backend the org has configured. Three data stores back everything: PostgreSQL, the Graph DB, and the Vector Store.

### 4.2 Component Breakdown

**Client — Next.js Visualization Shell** — React Flow/Sigma.js rendering switch at ~500 nodes; graphology behind a documented allowlist, never RBAC/traversal; Technical/Product/Onboarding tabs re-issue a graph query with a different view parameter; viewport-scoped querying; live WebSocket patching, including live-presence highlighting.

**API Gateway / Edge Layer (Node.js)** — AuthN via JWT/session validation; AuthZ middleware filters every request through RBAC before it reaches any data service. REST facade for MVP; GraphQL added later over the same service layer. Business logic is never written in route handlers, resolvers, or MCP handlers: the pattern is Route/Resolver/MCP-tool (thin) → Service Layer (real logic) → Graph Query Service → Graph DB.

**MCP Gateway (Node.js)** — Terminates MCP connections (streamable HTTP); authenticates per-org scoped API keys; attaches the same `{ agentKeyId, orgId, roles }` context the REST middleware attaches; dispatches to the same service-layer functions. Read-only tool surface at MVP. Rate limiting and per-tool call metering from day one.

**Model Provider Adapter (Node.js config / Python client)** — Per-org configuration (`model_provider`, `model_endpoint`, `model_credentials`) stored in Postgres, defaulting to Claude. One adapter interface implemented three ways: Anthropic-native, OpenAI-native, OpenAI-compatible-endpoint. Endpoint credentials read exclusively through the secrets loader (§4.5). Circuit-breaker/timeout wrapper with a configurable fallback per org. When configured for self-hosted, verified to make zero outbound calls to any third-party model endpoint via a network-isolated test.

**Core App Service (Node.js/TypeScript)** — Org/user/permission management, node sidebar metadata assembly, the Graph Query Service (viewport/view-filter requests → Cypher with RBAC-based node stripping), and Bucket CRUD (§2.11). Kicks off async jobs onto the message bus rather than doing heavy work inline.

**Realtime Service** — WebSocket gateway backed by Redis pub/sub for fan-out across multiple gateway instances; every push (including live-presence updates, §2.12) is re-filtered through the receiving client's RBAC scope before delivery.

**Async Worker Fleet (Python + FastAPI)**
- **Ingestion/Delta Worker** — clones/diffs, runs Tree-sitter, writes node/edge upserts, updates embeddings, publishes `graph.updated`. Operates against a scratch clone destroyed after parsing.
- **Semantic Enrichment Worker** — consumes newly parsed nodes on a separate queue; calls Graphify + LangChain/LangGraph + the configured Model Provider Adapter to build feature clusters, style tags, and onboarding step summaries; feature-cluster completion also triggers auto-bucket generation (§2.11).
- **Onboarding Priority Lane** — a dedicated priority queue drained ahead of general enrichment.
- **Retrieval Service (Graph-Guided RAG)** — resolves an anchor node, traverses a bounded number of hops, pulls only in-scope Vector Store chunks, calls the configured Model Provider Adapter with a bounded context window. Backs the MCP tools `find_relevant_nodes` and `traverse_from`.

**Integration Workers (Node.js)**
- **Git sync (provider-generic)** — webhook receiver validates signatures, normalizes events onto the message bus, updates ownership/PR/commit metadata directly on Graph DB node properties, and (new) handles open-branch push events for live presence (§2.12). Carries a `provider` field, normalized event schema, and pluggable auth from v1. Delta sync target: <5s.
- **Jira/Linear sync** — fully webhook-driven bidirectional sync via a BullMQ-backed worker, mapping ticket IDs to file/feature nodes, scoped to an admin-selected project/space allow-list per org. Target: <5s ticket-to-graph latency.

### 4.3 Data Model

**Relational Store (PostgreSQL)** — organizations, users, repositories, permissions (scoped by org/repo/branch/path), a ticket cache, style rules, onboarding steps, GitHub App installation records, MCP client credentials (per-org scoped agent API keys, revocation/audit fields), per-org Model Provider configuration, and per-org Jira/Linear project-space allow-lists. Row-level security enabled from the start.

**Graph Store (Neo4j, Neptune-compatible)** — node labels: Project, Repo, Folder, File, Function, Class, Module, Person, Commit, Feature, Ticket, EnvStep, Test, and Bucket (new). Edge types: CONTAINS, CONNECTS_TO, IMPORTS, CALLS, INHERITS, OWNS, AUTHORED, MODIFIED, REFERENCES, PART_OF, REQUIRES, DEPENDS_ON, COVERS, and (new) BUCKET_CONTAINS, BUCKET_MEMBER, WORKING_ON. All migrations openCypher-only.

- **Bucket node** — properties: `name`, `description`, `org_id`, `teamLeadPersonId`, `createdAt`, `updatedAt`, and `origin` (`auto-generated | manual`, set at creation and never overwritten — audit/badging only, no effect on capabilities).
- **BUCKET_CONTAINS edge** (Bucket → Folder / File) — bucket membership.
- **BUCKET_MEMBER edge** (Person → Bucket) — carries `role` (`lead | member`).
- **WORKING_ON edge** (Person → Folder / File) — ephemeral live-presence edge; carries `branchName`, `lastActivityAt`, `status` (`active | stale`). Written/refreshed by branch push events, expired after a configurable inactivity window, removed on merge/close.
- **EnvStep** gains a `scope` property: `global` or a `bucketId` reference.

**Vector Store (pgvector, OpenSearch-ready)** — code and doc chunks embedded and keyed back to their originating graph node ID, namespaced per organization.

### 4.4 Key Flow Walkthroughs

**Initial Repository Onboarding (cold start)** — Install GitHub App → install/OAuth callback stores credentials, enqueues `repo.initial_parse` → full-parse job runs (Tree-sitter, bulk graph write, full embedding pass) → Onboarding Priority Lane queues onboarding-step generation ahead of general feature clustering → Feature Clustering completes → auto-generated Buckets are created (§2.11) → Technical Tree becomes available.

**Steady-State Push Event (<5s sync target)** — Push triggers webhook → Ingestion Worker parses changed files, diffs the AST, writes upserts/deletes → publishes `graph.updated`, fanned out over WebSocket. Pushes to open (non-default) branches additionally refresh WORKING_ON edges for live presence (§2.12).

**AI Query (Graph-Guided RAG)** — User question → Retrieval Service resolves anchor node, traverses bounded hops, fetches in-scope chunks, calls the configured Model Provider Adapter — logging tokens used vs. a hypothetical full-repo count.

**Agent Context Query over MCP** — Agent calls `find_relevant_nodes`, then per node calls `get_agent_skill_md`, `get_style_rules`, `get_covering_tests` before proposing any change. Every call logged with org, agent key, node scope, and tokens served.

**Ticket Sync (<5s target)** — A Jira/Linear webhook event on an allow-listed project/space triggers a graph write mapping the ticket to file/feature nodes within 5s; if no explicit tag exists, the AI-inferred matcher (§2.8) attempts a match above threshold, otherwise the ticket surfaces as unmatched in the Ticket Inbox (§2.9).

### 4.5 Security & Multi-Tenancy

- **Tenant isolation is structural, not just a WHERE clause** — `org_id` stamped on every graph write and injected server-side on every query; vector store per-tenant namespaces; Postgres RLS as defense-in-depth. The Neo4j tenant guard enforces `org_id` scoping via structural means — real openCypher grammar parsing confirming `org_id` sits in an actual filtering position, or a query-builder API that cannot express an org-less query — not textual/regex proof of adjacency, since Neo4j Community has no engine-level backstop and this guard is the only thing standing between a mis-scoped query and cross-tenant disclosure.
- **Login CSRF / session-injection protection** — every login-initiating OAuth flow (GitHub and Google) binds the flow to the browser that started it via an `httpOnly`, `SameSite=Lax` state-binding cookie set at flow-start and verified at callback, before a session is ever minted.
- **Frame protection** — all login start/callback responses set `X-Frame-Options` / `frame-ancestors`.
- **Platform-wide rate limiting** — REST API, MCP Gateway, webhook receivers, and login routes sit behind configurable rate limiting: per-IP for unauthenticated routes, per-key/per-org for authenticated ones.
- **User-resolution hardening** — user lookup by external auth ID runs through a locked-down `SECURITY DEFINER` function plus a narrowly-scoped `NOLOGIN` / `NOBYPASSRLS` role, mirroring the installation-resolver pattern, rather than relying on a superuser RLS bypass.
- **GitHub repo org-exclusivity** — enforced server-side on every ingestion write and read (§2.4).
- **Jira/Linear space/project org-scoping** — enforced at the connection level via an admin-selected allow-list (§2.4).
- **Granular (node-level) access control** — enforced centrally in the Graph Query Service; unauthorized nodes filtered server-side before leaving the server. Same filter applies to WebSocket fan-out (including live-presence pushes) and every MCP tool response.
- **Bucket write-path RBAC** — bucket creation/editing/decline restricted to the Technical Lead role or an org admin; regular members get read-only visibility scoped by their existing canvas access.
- **MCP credential posture** — per-org scoped API keys, created/revocable from the canvas by org admins, stored and audited in Postgres alongside user permissions, scoped no wider than the issuing admin's own scope, metered per key.
- **Model Provider credential posture** — self-hosted endpoint URLs/credentials and hosted-provider API keys read exclusively through the secrets loader; switching an org's provider is an audited configuration change, not a code deploy.
- **Data ephemerality** — the Ingestion Worker operates against a scratch clone destroyed after parsing; only structural metadata and embeddings persist, never raw source trees.
- **Secrets (staged posture)** — MVP uses environment files behind a single loader module per language; on the trigger defined in §4.10, the loader backend swaps to a KMS-backed secrets manager and every previously issued secret is rotated.

### 4.7 Feature Cluster Visualization & Metadata Panel

Feature Clusters render as dashed boundary lines around the Folder/File nodes the Semantic Enrichment Worker groups into a Feature node. Clicking a boundary opens a panel with four fields: Description, Team, Files Included, Recent Edits. Feature membership is served to agents via `get_feature_cluster`, and also seeds auto-generated Buckets (§2.11).

### 4.8 Interactive Node Overlay Panel (Node-Level Toggles)

Six independently toggleable layers per Folder/File node: Dependencies, Recent Changes, Specific Features, Agent/Skill MD, Description, Specific Tickets. Agent/Skill MD is a dual-surface contract: the canvas is its authoring surface (RBAC-gated, versioned, attributed); its two runtime consumers are the platform's own Retrieval Service and external agents via `get_agent_skill_md`.

### 4.9 Folder-Level Topological Inheritance

Coding Style and Comment Style tagged once on a Folder node, tracked as separate properties, inherited by nested files unless overridden. Inheritance resolves top-down at query time; `get_style_rules` returns the same resolved answer the canvas displays.

### 4.10 Scaling & Migration Triggers

Every deferred migration is gated by a measured trigger, never a calendar date or customer count: Neo4j→Neptune, pgvector→OpenSearch, REST→GraphQL(+DataLoader), env-file→KMS secrets, MCP read-only→write/propose tools, Default-Claude→customer-selectable provider (design-time, not-load-gated), expanding self-hosted server-type support. Concrete threshold values are defined and documented as part of the migration dashboard's acceptance criteria.

### 4.11 Local-Model Interoperability for the Agent Context Layer

The MCP Gateway is, by protocol design, agnostic to what powers the client on the other end of the connection. A customer running an internal agent on a self-hosted open-weight model can be an MCP client against this platform's tool surface exactly as Claude Code or Cursor's IDE agent are today — same per-org scoped key, same RBAC-filtered responses, same tenant isolation, same metering. Requirements: interoperability verification (a real non-Anthropic, non-Cursor MCP client test), a published tool contract, and no change to auth/RBAC/metering for a locally-modeled agent.

## 6. Forward-Looking Integration: Cursor Origin

Cursor announced Origin, an agent-native git hosting platform, on June 16, 2026 — a git-compatible alternative to GitHub built around AI agents as primary users of version control. As of this writing it remains waitlist-only, GA targeted fall 2026, no public API/webhook documentation released.

Why it's relevant: with the Agent Context Layer, this platform is the MCP server; Origin's agents are clients. Origin's agents should connect to this platform's MCP surface the same way Claude Code, Cursor's IDE agent, and a customer's self-hosted-model agent do — with zero Origin-specific work on our side. The ingestion-side integration (Origin as a git provider) remains gated on Origin publishing public API/webhook documentation, plugging into the provider-generic Integration Worker as a new provider.

**Recommended approach:** keep the git Integration Worker provider-generic (hard requirement); do not build a concrete Origin ingestion integration until its documentation is public; the MCP surface requires no Origin-specific work.
